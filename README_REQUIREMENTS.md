# UIBench 项目理解与产品方向

> 更新时间：2026-08-10
> 当前命题：AI 生成高质量、可二次修改的移动端设计稿
> 当前载体：受约束、可寻址的 HTML 设计产物

## 一、核心结论

UIBench 下一阶段不应被定义成“让不同模型生成一段 HTML 的排行榜”，而应逐步演进为：

> 生成、筛选和持续修改高质量移动端设计稿的工作台。

HTML 仍然是当前最合适的设计稿载体，但 HTML 本身不是最终产品价值。真正需要建立的是四项能力：

1. **稳定生成**：根据产品需求生成多个可正常渲染的移动端设计方案。
2. **视觉质量**：通过设计规则、多候选、截图评价和自动修复，提高“好看”的稳定性。
3. **结构化编辑**：用户能够选中页面元素，用自然语言进行局部修改，而不是每次重写整页。
4. **版本闭环**：每次生成和修改都形成版本，支持撤销、回退、对比和继续编辑。

当前主目标仍是移动端设计稿。ArkUI 作为显式开启的实验性下游导出能力，不作为
UIBench 设计稿质量的成功标准，也不承诺生产应用代码可用。

## 二、当前 UIBench 的基础

当前仓库是用户 Fork 后的项目：

- 仓库：`https://github.com/Davont/UIBench.git`
- 分支：`main`
- 当前基线提交：`acd2741b652569c1fdbc8288f426a9904801d4be`
- 应用版本：`0.5.0`

UIBench 是一个 FastAPI 单体应用，当前主要流程是：

1. 用户输入 UI 需求并选择生成模式。
2. 后端读取配置中启用的多个模型。
3. 同一需求被并行发送给各模型。
4. 结果通过 NDJSON 流式返回，先完成的模型先展示。
5. 模型输出被提取为 HTML，在 sandbox iframe 中渲染。
6. 原始输出、reasoning、HTML、耗时和错误写入日志。

与新命题直接相关的现有优势：

- 已有多模型并行生成能力，可以自然扩展为“多候选设计生成”。
- 已有浏览器 HTML 渲染能力，可以继续增加截图和视觉评价。
- 已有流式返回能力，能够逐步展示候选方案，降低等待感。
- 已有生成日志，可以扩展为设计版本、Prompt 版本和评价数据。

当前主要缺口：

- 生成仍以一次性、任意 HTML 为主。
- 视觉质量主要依赖单次 Prompt，没有形成评价和修复闭环。
- DOM 结构不稳定，无法可靠定位用户选中的元素。
- 移动端已经落地 HarmonyOS、Spotify、Netflix、Notion 四套 Design Token，
  且每套支持 Light/Dark。v6 已拆分不透明背景层级、组件弱填充、轮廓与列表分割线；
  尚需用新生成样本验证 Token 引用率、风格迁移质量以及跨页面一致性。历史 HTML 仍包含
  硬编码样式。
- 没有局部修改协议、版本管理和方案对比。
- 当前 README 对 PC 模式、流式返回等实际能力的描述不完整。

此前同一代码基线的离线测试结果为 `32 passed`，另有一个 Starlette/httpx 弃用警告，不影响当时测试结果。后续开始实现新方案前，应在当前新克隆仓库中重新执行一次基线测试。

## 三、为什么现阶段选择 HTML

“模型接触过大量 HTML/CSS 素材”是选择 HTML 的一个理由，但不是唯一理由。更重要的是：

- 主流模型对 HTML/CSS 的生成能力相对成熟。
- 浏览器是稳定、低成本、即时可用的渲染器。
- HTML 可以直接生成截图，便于视觉评价和版本对比。
- DOM 天然具有层级结构，适合选中、定位和局部替换。
- CSS Variables 适合承载颜色、字体、间距和圆角等 Token。
- 设计师和工程师都能直接查看、调试和人工修正。

因此，应继续生成 HTML，但不能继续允许完全自由的 HTML。目标是生成：

> 受约束、可寻址、可局部修改的 HTML。

## 四、设计产物模型

建议把一次设计结果视为一个版本化的设计产物，而不是一段孤立字符串：

```text
design-version/
├── screen.html       # 可直接渲染的移动端页面
├── tokens.json       # 颜色、字体、间距、圆角、阴影等设计变量
├── manifest.json     # 页面节点、组件语义和可编辑属性
└── preview.png       # 固定视口下的视觉快照
```

四部分各自解决不同问题：

| 产物 | 作用 |
| --- | --- |
| `screen.html` | 浏览器渲染和人工调试 |
| `tokens.json` | 全局风格控制与主题切换 |
| `manifest.json` | 元素定位、局部修改和编辑约束 |
| `preview.png` | 视觉评价、候选排序和版本对比 |

### 可寻址 HTML

每个重要页面元素应具备稳定标识和组件语义：

```html
<section
  data-node-id="home.hero"
  data-component="hero"
>
  <h1 data-node-id="home.hero.title">
    开启你的健康生活
  </h1>
</section>
```

用户点击标题后，系统可以明确下发：

```json
{
  "target": "home.hero.title",
  "operation": "update-content",
  "instruction": "标题更轻松一些，控制在 12 个字以内"
}
```

模型只修改目标节点或目标子树，未选中的区域默认保持不变。

### 生成代码约束的目的

代码约束服务于设计稿的可靠生成和二次编辑：

- 重要元素必须有稳定 `data-node-id`。
- 常用模块通过 `data-component` 标明组件语义。
- 重复内容使用明确的数据结构和模板，避免复制大量近似 DOM。
- 布局优先使用可预测的 Flex/Grid，限制无必要的绝对定位。
- 样式优先引用语义 Token，减少散落的硬编码值。
- 生成 HTML 不包含业务逻辑；选择、编辑和版本能力由工作台运行时提供。
- 外部资源采用白名单或受控素材库，避免任意 CDN 破坏可复现性。

这些规则首先服务于设计稿可靠生成和局部编辑；显式开启 ArkUI 导出时，同一批稳定
节点和组件语义也会作为 UIBench 适配层输入，但不会改变主产品的验收目标。

## 五、Design Token 的定位

Design Token 在当前命题中的作用是：

> 保持视觉一致性，并让全局风格调整不必重新生成页面结构。

建议至少覆盖：

- 颜色：背景、表面、正文、弱文本、主操作、状态色。
- 字体：字体族、字号、字重、行高和字间距。
- 空间：页面边距、区块间距、组件内边距和元素间距。
- 形状：圆角、边框和阴影。
- 动效：时长和缓动，但仅允许受控的展示型微交互。

Web 端最终通过 CSS Variables 使用 Token：

```css
:root {
  --color-primary: #6750a4;
  --color-surface: #ffffff;
  --color-text-primary: #1d1b20;
  --radius-card: 20px;
  --space-section: 24px;
  --font-title: 28px;
}
```

用户提出“换成更温暖的配色”“整体紧凑一些”“圆角小一点”时，系统应优先生成 Token Patch，而不是重新生成整页 HTML。

Token 可以使用 DTCG 格式作为长期存储规范，但第一版无需同时开发跨平台 Adapter。

## 六、怎样提高“好看”的稳定性

单纯增加 Prompt 长度，或者安装一个 taste-skill，都不能稳定解决审美问题。更合理的是建立完整生成管线：

```text
用户需求/参考图
       ↓
需求理解与视觉方向
       ↓
生成 4～8 个候选方案
       ↓
浏览器渲染与截图
       ↓
结构规则检查 + 视觉评价
       ↓
对高潜力方案自动修复一次
       ↓
用户选择并继续修改
```

视觉评价至少检查：

- 信息层级是否清晰。
- 留白和视觉密度是否合理。
- 对齐、圆角、字体和颜色是否一致。
- 主操作是否突出但不过度。
- 文本对比度、字号和触控区域是否合格。
- 是否存在文字溢出、遮挡、横向滚动或布局断裂。
- 是否存在明显的模板化 AI 风格和无意义装饰。
- 是否忠实覆盖用户需求，没有随意增加业务功能。

同一个模型既生成又评价会产生偏差。第一版可以将确定性规则检查与视觉模型评价结合，并把用户最终选择作为最重要的真实偏好数据。

### taste-skill 的使用方式

taste-skill 更适合作为以下内容的参考来源：

- 生成阶段的审美规则。
- 截图评价阶段的检查清单。
- 自动修复阶段的设计建议。
- anti-slop、减少模板化 AI 风格的规则。

不建议把其完整原文直接拼入 System Prompt：

- 默认规则主要偏向 Landing Page、Portfolio 和 Redesign。
- 部分规则倾向补充 Hero、CTA、导航等用户没有要求的内容。
- 对外部图片、动效库和 JavaScript 的偏好与当前移动端约束有冲突。
- 上游仍可能变化，会影响评测的可复现性。

如果进行实验，应固定版本，只提取适合移动端产品页面的规则，并保留 baseline、tokens、taste、tokens+taste 四组对照。

## 七、二次修改机制

建议把编辑能力分成四级：

### 1. 全局风格修改

修改 `tokens.json`，适合配色、字体、圆角、间距和整体密度调整。

### 2. 单元素修改

通过稳定节点 ID 修改指定元素的文案、图标、颜色、尺寸或状态。

### 3. 组件级修改

只重新生成某个卡片、导航栏、列表区或 Hero 区域，并替换对应 DOM 子树。

### 4. 整页重设计

生成一个新的完整版本，原版本继续保留，用户可以对比和回退。

第一版推荐的编辑交互是：

> 点击选中元素 + 自然语言修改 + 版本回退。

暂时不追求 Figma 级自由拖拽、任意图层编辑和完整属性面板。它们会把问题从“AI 设计工作台”扩大成“重新实现一套专业设计工具”。

## 八、对原始三个需求的重新解释

### 需求 2：添加 Design Token，看看风格如何迁移

保留，但目标调整为：

- 验证相同页面结构下，仅切换 Token 是否能稳定改变风格。
- 验证全局风格修改是否可以避免重新生成整页。
- 衡量 Token 引用率、结构保持率和视觉一致性。

### 需求 3：添加 taste-skill，看看优化效果

保留为受控实验：

- 固定 taste 规则版本。
- 裁剪与移动端产品设计不兼容的规则。
- 同一需求、同一模型、同一参数做匿名对照。
- 通过截图评价和用户偏好验证是否真正改善，而不是凭主观印象判断。

### 需求 4：约束代码生成

保留，但目标调整为：

- 让 HTML 可稳定渲染。
- 让页面元素可以被定位和选中。
- 支持 Token Patch、节点 Patch 和子树替换。
- 保证修改局部时其他区域尽量不变。

不再默认解释为 ArkUI 或 D2C 转换需求；只有请求显式开启 ArkUI 导出时才附加对应合约。

## 九、建议的 MVP

第一版只包含：

- 移动端单页面设计稿。
- 以 390px 为主要设计宽度，同时验证 360px 和 430px。
- 一次生成多个候选设计。
- HTML 使用受约束结构，并为重要元素生成稳定节点 ID。
- 使用统一 Design Token。
- 自动渲染截图并进行基础规则检查。
- 支持点击选中元素和自然语言局部修改。
- 支持主题级修改。
- 支持撤销、回退和版本对比。

第一版暂不包含：

- 生产级 ArkUI 生成或转换（实验性结构导出不计入 MVP 验收）。
- D2C 工程。
- PC、平板等多端设计。
- Figma 级自由拖拽。
- 复杂业务逻辑和完整应用运行时。
- 生产级前端代码导出。

## 十、建议实施顺序

### 阶段 1：建立可复现基线

- 建立固定移动端需求集。
- 记录模型、参数、Prompt 版本和生成耗时。
- 固定视口渲染并归档截图。
- 保留现有 Prompt 作为 baseline。

### 阶段 2：设计产物与 Token

- 定义 `screen.html`、`tokens.json` 和 `manifest.json`。
- 为重要节点生成稳定 ID。
- 把颜色、字体、间距和圆角外置为 Token。
- 验证只修改 Token 时 DOM 结构保持不变。

### 阶段 3：多候选与视觉评价

- 同一需求生成多个视觉方向。
- 增加渲染失败、溢出、遮挡、对比度和触控区域检查。
- 引入视觉模型评价和一次自动修复。
- 保存用户最终选择，形成偏好数据。

### 阶段 4：局部编辑与版本管理

- 实现页面元素选中。
- 定义受限 Patch 协议。
- 支持 Token、节点、组件子树三类修改。
- 增加撤销、版本回退和并排对比。

### 阶段 5：taste 对照实验

- 固定并裁剪 taste 规则。
- 运行 baseline、tokens、taste、tokens+taste 对照。
- 根据真实指标决定哪些规则进入正式 Prompt。

## 十一、建议验收指标

| 维度 | 建议指标 |
| --- | --- |
| 渲染可靠性 | HTML 成功渲染率、无严重控制台错误 |
| 视觉质量 | 匿名两两比较胜率、用户选择率 |
| 需求忠实度 | 必要内容覆盖率、无依据功能新增数量 |
| 响应式 | 360/390/430px 无溢出、遮挡和横向滚动 |
| 风格一致性 | Token 引用率、硬编码样式数量 |
| 编辑局部性 | 修改目标外 DOM/截图变化比例 |
| 编辑成功率 | 一次修改成功率、平均重试次数 |
| 可恢复性 | 所有修改可撤销、版本可回退 |
| 性能与成本 | 首个候选耗时、全部候选耗时、单方案成本 |

其中最关键的不是某个模型自评得分，而是：

- 用户在候选方案中选择了哪一个。
- 用户第一次生成后需要修改多少次。
- 修改一个局部时，其他区域是否保持稳定。
- 同一需求重复生成时，质量是否足够稳定。

## 十二、当前边界与后续可能性

当前阶段应先验证两个核心假设：

1. AI 能否稳定生成让用户愿意继续使用的移动端设计稿。
2. HTML + Token + 稳定节点能否支持可靠、低成本的二次修改。

当前可以并行验证实验性 ArkUI 结构导出，但只有这两个假设成立，才值得把生产代码
导出、ArkUI、其他平台 D2C 或更复杂的设计工具能力提升为主产品目标。它们仍是可选
下游，不是当前产品成立的前提。
